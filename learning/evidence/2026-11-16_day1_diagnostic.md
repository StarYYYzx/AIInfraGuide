## 诊断题（会话开始，讲解前）

- 问题：请用自己的话说明 Prefill 和 Decode 分别在做什么。
- 用户原回答：自述尚未开始学习，说不出来。
- 结论：零基线确认，Day 1 合法开局；进入讲解。

## 独立复述（讲解 §1–3 后）

- 用户复述原文（摘要）："Prefill 的全过程，是把 prompt 先 token 化，然后一次性并行塞入 LLM 进行计算，然后得到若干'参数'；然后 Decode 过程中，利用这些'参数'，结合前面的 token，预测下一个 token……直到预测到终止符。"
- 判定：主干正确（token 化在前、并行整段进网络、串行依赖、终止于 EOS）。
- 错误与缺失（AI 指出）：
  1. 把 Prefill 产出称为"参数"——概念错误，应为 KV Cache（运行时生成的 K/V 中间结果），与模型权重 W 严格区分；
  2. 缺失 Prefill 产出第 1 个输出 token（两阶段分界）；
  3. 缺失 Decode 每步新 token 完整过网络、自身 K/V 追加进缓存。

## 修正后复述（第二次，未直接看答案文本）

- 用户复述原文（摘要）："Prefill：将 token 化的 prompt 一次性并行塞给模型，得到 KV cache，基于 KV cache 以及 prompt 的所有 token，预测并生成第一个 token；Decode：基于前面已生成 token，更新 KV cache，然后基于 KV cache，预测下一个 token，反复循环，直到生成终止符。"
- 判定：**通过**。三处修正均吸收，机制层面准确。I11 §1–2 记 explained。
- 追问澄清记录：用户主动提出两个问题——①一个 token 对应多少文字；②"一次性并行"如何理解。AI 给出换算量级（中文 1 字 ≈ 1–2 token）与并行机制解释（Prefill 输入全部已知可整批 GEMM；Decode 第 t+1 步输入依赖第 t 步输出，天然串行）。
- 概念辨析记录：用户问"KV Cache 的作用是否类似权重"。AI 指出共性（同住显存、每步必读）与本质区别（固定共享的变换规则 vs 每请求私有、逐步增长的中间状态），二者是两条独立优化战线（权重量化 vs GQA/PagedAttention）。

## Memory-bound 验收题（未通过）

- 问题：为什么每步只算 1 个 token 的 Decode 是访存受限？
- 用户原回答（摘要）："伴随 token 量增加，要调用的 KV cache 和权重都越来越多……从显存中调用的数据量是 O(n²)，时间花费取决于从显存取数据的速度。Decode 每预测一个 token，既要调用显存中固定的权重，又要调用显存中临时存放的 KV cache。"
- 判定：**结论正确，机制部分错误，不通过**。
  - ✅ 正确：每步读取对象识别正确（固定权重 + KV Cache）；时间由显存取数速度主导的结论正确。
  - ❌ 错误一："权重越来越多"——权重固定不变，每步读取的字节数恒定；随上下文增长的是 KV Cache（每步 O(n)，整次生成累计 O(n²) 仅对 KV 读取成立）。
  - ❌ 错误二：未触及核心判据"算术强度"。即使上下文很短（如第 2 步），Decode 也是访存受限——每步读取整个权重矩阵（GB 级）却只换回 1 个 token 的计算（GEMV vs Prefill 的 GEMM，同样读一次权重，计算量差数百倍）。
- AI 提示已给出（讲解轮的对照表：同样读一次权重，Prefill 换回 500 份计算，Decode 只换回 1 份），用户回答未使用该判据，故记为提示后仍未独立复现。
