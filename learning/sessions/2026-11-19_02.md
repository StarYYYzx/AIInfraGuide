## 用户提问与 AI 讲解（全部为讲解，非掌握证据）

1. **lm_head / h_last / W_lm / logits 三个术语**（用户两次提问，说明上一轮讲解过密）：
   - h_last (d,)：最后一行隐藏状态（"读完全文的理解摘要"）；
   - W_lm (d, V)：LM Head 权重矩阵（每列=词表一个候选的代表向量；LLaMA-3 口径 ≈1.2 GB）；
   - logits (V,)：原始打分（任意实数，非概率）；
   - lm_head = 以 W_lm 为核心的输出模块，与入口嵌入层方向相反（查表 V→d 取行 vs 矩阵乘 d→V 打分）。
   - 完整尾巴：h_last·W_lm → logits → softmax（含温度 logits/T）→ 采样（greedy/温度/top-p/top-k）→ id → tokenizer 反向映射还原文字（CPU 侧；字节级 token 可能切在多字节汉字中间，流式拼接是前端问题）。
2. **Tensor Core vs CUDA 核心**：同 SM 内两类单元；CUDA 核心=通用 FP32 工人（逐元素/softmax/残差），Tensor Core=专用 MMA 矩阵乘累加单元（低精度高吞吐，H100 每 SM 4 个，gpu-basics 行 87/108）；推理分工=矩阵乘归 TC、逐元素归 CUDA 核心；"两种单元都闲着等显存"是访存受限的微观表现。
3. **Decode 时序精修**：用户总结"每次预测一个，然后把这个向量的 k/v 放入 cache 供给后面"——功能层正确；AI 精修两点：①追加的是**本轮输入 token**（=上一步预测结果）的 k/v，追加发生在打分之前，所以注意力含"看自己"（掩码对角线为 0 的原因）；②追加的是每层各自的 k/v（32 层 32 组），不是隐藏状态本身。
4. **Prefill 的限制（条件化）**：长 Prompt→Compute-bound（大 GEMM）；短 Prompt→向访存受限滑落；超长上下文→注意力 O(N²) 项；任何情况→显存容量下限（OOM/换页断崖）；服务视角→排队调度。
5. **显存大小 vs 运算速率**：三条独立轴——容量（GB，决定"能不能跑/多少并发"）、带宽（GB/s，决定 Decode 速度）、算力（TFLOPS，决定 Prefill 速度）；容量≠速度（A100/H100 同 80GB 不同速；4090 24GB 高算力）；联系带宽与算力的是 Roofline（gpu-basics §3.3），不是容量。
6. **CoT 与 KV Cache / 上下文与 KV Cache**：
   - CoT token 与普通 token 同等对待，逐层产生 k/v 追加缓存；长 CoT → 缓存膨胀（1 万 token ≈ +5 GB @0.5MB/token 例）且每步 Attention 读全量 → 推理模型更贵更慢的结构性原因；跨轮是否保留 CoT 是应用层选择（不进上下文就不进缓存）。
   - **上下文与缓存一一对应**：上下文 N 个 token ↔ 每层缓存 N 行 k/v；"128K 窗口"= 缓存最多 128K 行（≈64GB @0.5MB/token）；上下文范围大于"聊天记录"（含模板/系统提示/工具输出/CoT）；Prefix Cache（模块四 2.3）是该对应关系兑现的工程红利。
